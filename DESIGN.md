# SVG Importer 3: Native Import Core

Status: proposal · Owner: Jaroslav Stehlík · Last updated: 2026-10-24

This document plans the next modernisation step of SVG Importer: replacing the C# SVG parser and tessellator with established native libraries, while keeping the Unity side (importer, Inspector, render formats, modifiers) in C#. It also plans the samples and the documentation.

Version 2.0 (the `modern` branch) already made the plugin a UPM package for Unity 6 with URP support and a `ScriptedImporter`. This plan builds on that.

## 1. Goals

1. **Parse SVG robustly.** Real-world files from Illustrator, Inkscape, Figma, Affinity and browsers should import correctly, including CSS, `<use>`/`<symbol>`, nested transforms, gradients in both unit systems, clip paths and text.
2. **Tessellate robustly and fast.** Correct fills for any path (self-intersections, holes, both fill rules), proper strokes (joins, caps, miter limits, dashes), no cracks, no crashes.
3. **Keep everything Unity-specific in C#.** The Inspector, the render formats (Opaque, Transparent, uGUI), depth handling, the gradient atlas, layers for modifiers, colliders and serialization stay as they are, so existing projects and APIs keep working.
4. **Measure quality.** A conformance corpus with reference images gives a support percentage that we track over time, instead of discovering failures from user reports.
5. **Ship samples as Unity samples and documentation as package documentation.**
6. **Make every cost visible and optional.** By default an SVG costs one mesh, one shared material, one batched draw call and no render targets. Anything that creates a render target, adds a material or draw call, or adds a render pass is an explicit opt-in setting on the asset or the component, and the setting states its cost. Where the cheap default is an approximation, the Inspector says so. Each SVG Asset shows a cost summary: vertices, triangles, materials, draw calls, render targets and texture memory.

### Non-goals

- Rendering SVG at runtime with a vector renderer. SVG Importer bakes meshes at import time; that is its main advantage on mobile.
- Supporting SVG features that cannot become a mesh: filter effects, blending modes and, in general, luminance masks. They are reported as warnings.
- Changing the runtime data model (`SVGAsset`, `SVGLayer`, `SVGShape`) beyond additions.

## 2. Today

```
.svg ─► C# XML parser (SmallXmlParser) ─► C# SVG DOM ─► C# path flattening
     ─► Clipper (C#) + LibTessDotNet (C#) ─► SVGLayer[] / SVGShape[]
     ─► SVGMesh.CombineMeshes (format, depth, gradients) ─► SVGAsset (Mesh, shaders, gradients, layers, collider)
```

The pipeline after `SVGLayer[]` is Unity-specific and works well. The part before it is the problem:

- The parser is a hand-written partial SVG 1.1 implementation from 2015. Recent fixes (gradient units, radial radius) show how much of the spec is approximated. CSS support is minimal and there is no text support.
- Tessellation uses LibTessDotNet, a C# port of SGI libtess. It is robust but slow, and strokes are generated by custom code.
- There is no test corpus. Support is described by a feature list in the README, not measured.

## 3. Targets

Meshes are baked at import time, so most of the work happens in the Unity Editor. The core also runs in players, so that `SVGAsset.Load` can import SVG at runtime on devices (section 8).

| Target | Rust target | Library | Used by |
|---|---|---|---|
| Windows x64 | `x86_64-pc-windows-msvc` | `svgimporter_core.dll` | Editor, standalone player |
| Linux x64 | `x86_64-unknown-linux-gnu` | `libsvgimporter_core.so` | Editor, standalone player |
| macOS universal (arm64 + x64) | `aarch64-apple-darwin` + `x86_64-apple-darwin`, merged with `lipo` | `libsvgimporter_core.dylib` | Editor, standalone player |
| iOS arm64 | `aarch64-apple-ios` | `libsvgimporter_core.a` (static) | Player |
| Android arm64 | `aarch64-linux-android` | `libsvgimporter_core.so` | Player |

Not targeted: Windows and Linux on arm64, 32-bit Android (armv7), WebGL and consoles. On these platforms, importing in the Editor isn't available (the importer reports a clear error), and players use the meshes baked at import time, as they always have. Only runtime import is unavailable there (section 8).

## 4. Library selection

### 4.1 Parser

| Library | Language | License | Notes |
|---|---|---|---|
| **usvg** (resvg project) | Rust | Apache-2.0 OR MIT | Parses SVG into a simplified, fully resolved tree: shapes become paths, styles and CSS are resolved, `<use>` and `<symbol>` are expanded, and text can be converted to paths with real fonts. It comes from the resvg project, which maintains a large SVG test suite with a published support table comparing it to browsers. It is actively maintained (v0.49.0 released 2026-10-24) and has about 4,100 GitHub stars. |
| ThorVG | C++ | MIT | Complete vector engine with SVG and Lottie loaders, used by Godot and Tizen. Its tessellator is internal to the GL renderer, not a separate API, and the loader is tied to its scene graph. |
| LunaSVG / PlutoSVG | C++ / C | MIT | Built for rendering to bitmaps. Smaller community, less complete CSS. |
| NanoSVG | C | Zlib | Single header, tiny and fast, but deliberately minimal: no CSS cascade, no text, limited `<use>`. Not robust enough for arbitrary files. |
| librsvg | Rust/C | LGPL-2.1 | Very complete, but the LGPL license and the cairo/glib dependency chain don't suit a redistributed Unity plugin. |
| Unity Vector Graphics | C# | Unity Companion License | Unity's own importer. Bound to Unity's license and API, and we would compete with the importer it already provides. |

**Choice: usvg.** It does the hardest part of SVG, resolving the document, better than any other library with a friendly license. It outputs exactly what a tessellator needs: absolute paths with resolved paint and transforms. Its test suite also gives us a ready-made conformance corpus.

### 4.2 Tessellator

| Library | Language | License | Notes |
|---|---|---|---|
| **lyon** (`lyon_tessellation`) | Rust | MIT OR Apache-2.0 | Fill tessellator (sweep line, both fill rules, self-intersections) and stroke tessellator (joins, caps, miter limit, per-vertex normals). Flattening tolerance is configurable. Widely used in Rust graphics. Actively maintained: `lyon_tessellation` is at 1.0.23 and was updated 2026-10-23. |
| libtess2 | C | SGI Free B | What we use today, in its C# port. Robust, slower, fill only. |
| earcut | C++/C# | ISC | Very fast, but only for simple polygons with holes. It can't handle self-intersections or fill rules without pre-processing. |
| Clipper2 | C++/C# | BSL-1.0 | Polygon boolean operations, not a tessellator. A candidate for clip paths. |
| i_overlay | Rust | Apache-2.0 | Polygon boolean operations in Rust, a candidate for clip paths (see 6.4). |

**Choice: lyon**, with `i_overlay` (or Clipper2) for boolean operations. The parser and tessellator then share one language and one build. lyon's stroke tessellator also returns the per-vertex normals that our antialiasing fringe needs today (`SVGShape.angles`).

### 4.3 Why Rust, and not C# or C++

- **Robustness:** the core parses untrusted input. A crash in a native plugin takes down the Unity Editor. Safe Rust removes the memory-safety class of crashes, and panics can be caught at the boundary (6.6).
- **Speed:** native code is much faster than the current C# for both parsing and tessellation, which matters most for runtime import on phones. We will measure it rather than assume (phase 0 sets the baseline).
- **The best libraries are already Rust.** For C# we would have to port them, which is how we got the current state. For C++, ThorVG is the only comparable option, and its tessellator isn't exposed.
- **Portability cost is moderate:** five targets (section 3), all of which Rust supports in its top tiers. iOS and Android need a little extra build setup (section 9).

The cost is a Rust toolchain for contributors who change the core. Contributors who only change the Unity side need nothing new, because the binaries ship prebuilt in the package.

## 5. Architecture

```
 ┌───────────────────────────── native: svgimporter-core (Rust) ─────────────────────────────┐
 │  .svg bytes ─► usvg (parse, resolve CSS/use/units/transforms, text → paths)               │
 │            ─► clip paths: boolean ops (i_overlay)                                         │
 │            ─► fills: lyon FillTessellator      strokes: dash (tiny-skia-path) + lyon Stroke │
 │            ─► AA fringe: lyon stroke of the outline, with normals                          │
 │            ─► flat result buffers (layers, vertices, indices, paints, diagnostics)         │
 └──────────────────────────────────────── C ABI ────────────────────────────────────────────┘
 ┌──────────────────────── C#: SVGImporter.Runtime (+ Editor for the importer) ───────────────┐
 │  SVGNativeCore (P/Invoke, blittable structs) ─► SVGLayer[] / SVGShape[] / SVGFill          │
 │  ─► existing pipeline: SVGMesh.CombineMeshes (Opaque depth / Transparent order / uGUI),    │
 │     gradient atlas (CCGradient), collider shape, layers for modifiers                     │
 │  ─► SVGFileImporter ─► SVGAsset                                                            │
 └────────────────────────────────────────────────────────────────────────────────────────────┘
```

**The boundary is `SVGLayer[]`.** Everything downstream of it is Unity-specific and stays in C#, unchanged. The native core replaces only what produces the layers today. That keeps the change testable: for the same SVG, both paths produce layers that we can compare.

## 6. Native core

### 6.1 Pipeline

1. **Parse** with usvg. Options passed from C#: DPI, default font family, a font directory, and whether to convert text.
2. **Walk the tree** in document order. Each path that has a fill and/or a stroke produces one layer, in the order the shapes are painted. Groups pass their transform and opacity down. Each layer carries the element `id`, which modifiers and future per-layer features key on.
3. **Fill:** tessellate with lyon using the path's fill rule (`nonzero` or `evenodd`) and a tolerance derived from the import's *Quality* (vertices per meter) and *Scale* settings.
4. **Stroke:** apply the dash array with tiny-skia-path if there is one, then tessellate with lyon's stroke tessellator (width, joins, caps, miter limit).
5. **Clip paths:** intersect the flattened geometry with the clip path polygon before tessellation. For `clipPathUnits="objectBoundingBox"`, usvg provides the bounding box.
6. **Antialiasing:** if enabled, produce the fringe as a zero-width stroke of the shape outline, emitting lyon's per-vertex normals. This matches today's `SVGShapeType.ANTIALIASING` shapes, so the existing antialiased shaders keep working.
7. **Paint:** output solid colors, or gradient descriptions (linear/radial, spread method, stops, gradient-to-shape transform). C# turns these into the existing gradient atlas entries and UVs, exactly as today.
8. **Diagnostics:** report unsupported features (masks, filters, images, blend modes) with element ids, and parse errors with line numbers. These replace today's `SVGError` flags; the old flags stay for compatibility.

### 6.2 What stays in C#

- `SVGFileImporter` and the Inspector, with the same settings and field names.
- Render formats: Opaque (per-layer depth offsets, *Compress Depth*), Transparent (painter's order), uGUI.
- Gradient atlas and gradient UV encoding, shaders, materials and the URP/Built-in support.
- Layers for modifiers (*Use Layers*), collider generation, pivot, 9-slice border, mesh compression, normals and tangents.

### 6.3 C ABI

The ABI is a small set of blittable structs and three functions. Written in Rust, shown here as C:

```c
typedef struct { float dpi; float tolerance; uint8_t antialiasing; uint8_t convert_text; const char* font_dir; } SvgiOptions;

typedef struct {
    uint32_t vertex_offset, vertex_count;   // into vertices (float2) and normals (float2, AA only)
    uint32_t index_offset, index_count;     // into indices (uint32)
    uint32_t paint;                         // into paints
    uint8_t  kind;                          // 0 fill, 1 stroke, 2 antialiasing
    uint32_t name_offset, name_length;      // element id, UTF-8, into strings
} SvgiLayer;

typedef struct {
    uint8_t  type;                          // 0 solid, 1 linear, 2 radial
    float    color[4];                      // solid color, opacity applied
    float    transform[6];                  // gradient space to shape space
    float    x1, y1, x2, y2, r, fx, fy;     // gradient geometry
    uint8_t  spread;                        // pad, reflect, repeat
    uint32_t stop_offset, stop_count;       // into stops (offset + color)
} SvgiPaint;

int32_t  svgi_import(const uint8_t* svg, size_t length, const SvgiOptions* options, SvgiResult** result);
void     svgi_free(SvgiResult* result);
uint32_t svgi_version(void);
```

**The C# side is generated, not written by hand.** [csbindgen](https://github.com/Cysharp/csbindgen) (MIT, by Cysharp, built for .NET and Unity) runs in the core's `build.rs` and generates `NativeMethods.g.cs`: the `[DllImport]` declarations and matching `[StructLayout(LayoutKind.Sequential)]` structs. The generated file is committed in the package's Editor assembly, and CI fails if it differs from a fresh build, so the two sides can't drift apart. A thin hand-written `SVGNativeCore` class wraps the generated calls in safe C# (pinning input, copying results, freeing native memory, turning error codes into exceptions).

Alternatives considered:
- **interoptopus** (MIT) generates a richer, safer C# layer: services as disposable classes, slices, strings, and Rust `Result`s as exceptions. That would replace most of `SVGNativeCore`. However, its current C# backend (0.16) emits `[LibraryImport]` with `static partial` methods, which need .NET 7's interop source generator. Unity's Mono and IL2CPP don't have it, so the output doesn't compile in Unity. The Unity flavour from 0.10 onwards now lives in the project's `crates/_old` folder. Worth revisiting if a Unity/`DllImport` output returns, or if Unity moves to CoreCLR.
- **uniffi-bindgen-cs** (MPL-2.0) follows Mozilla's UniFFI model, which is a heavier fit for a three-function API.

All arrays live in one allocation owned by the native side. C# copies them into managed arrays in one pass and calls `svgi_free`. No callbacks, no state between calls, and no threading assumptions, so imports can run in parallel in Unity's import worker processes.

### 6.4 Clip paths and masks

- **Clip paths:** supported by polygon intersection before tessellation. This fixes today's "experimental" clip paths and the unsupported `objectBoundingBox` units.
- **Masks:** a mask whose content is a single opaque shape can become a clip path. Other masks can't be represented as geometry and produce a warning.

### 6.5 Text

usvg converts text to paths using fonts. In the Editor we pass the system font directories plus a project font folder from the settings. At runtime on devices, system fonts aren't reliably available, so runtime import only uses fonts the project ships (passed as font data), or skips text with a warning. Files that use fonts which aren't available fall back to a default font and produce a warning. This removes the current "convert text to curves" requirement in most cases.

### 6.6 Crash safety

- Every exported function wraps its body in `catch_unwind` and returns an error code instead of unwinding into C#.
- Guard against pathological input: limits on document size, nesting depth, `<use>` expansion and output vertex count. Exceeding a limit is a reported error, not a hang.
- Fuzz with `cargo-fuzz` in CI.

## 7. Integration in Unity

- **Plugin files:** `Runtime/Plugins/<platform>/` inside the package. Each library's import settings enable it for its OS and CPU only: for Editor and standalone on Windows, Linux and macOS, and for the player only on iOS and Android.
- **C# wrapper:** the generated `NativeMethods.g.cs` plus the hand-written `SVGNativeCore` in the `SVGImporter.Runtime` assembly, because players use it too. On iOS the library is linked statically, so the import name is `__Internal` there; csbindgen generates that switch. On platforms without a library, `SVGNativeCore.isSupported` is false. `SVGNativeCore` checks `svgi_version()` against the version it was built for and shows a clear error if the binary is missing or mismatched.
- **Converter:** a `SVGNativeConverter` (in the runtime assembly, shared by the importer and `SVGAsset.Load`) maps the result into `SVGLayer`/`SVGShape`/`SVGFill`. The existing `SVGMesh.CombineMeshes` then runs unchanged.
- **Engine setting:** during the transition, a project setting *Import Engine: Native / Legacy* selects the core. The importer version is bumped when the default changes, so every `.svg` reimports once. The legacy engine is removed after phase 3.
- **Legacy `.asset` SVG Assets:** unaffected. They keep their baked meshes and can still be reimported with the legacy engine until it is removed. The converter (`Window > SVG Importer > Convert SVG Assets to SVG Files`) moves them to the new path.

### 7.1 Gradient rendering

All gradients in loaded SVG Assets share one atlas texture, filled on demand, so that every SVG mesh can use the same material and batch. The idea stays; the implementation is replaced, because gradients render with visible artefacts on some hardware, especially Android.

**Problems in the current implementation (2.0 and earlier):**

| Symptom | Cause |
|---|---|
| Colours of other gradients bleed in | The colour atlas packs 128×4 gradient tiles edge to edge, four per row. The shader samples tiles 0, 4, 8… on the top texel row of their 4-texel strip and tiles 3, 7, 11… on the bottom row, right on the border with the neighbouring strip. Any coordinate imprecision, more common on mobile GPUs, blends in the neighbouring gradient. |
| Bleeding at the ends of a gradient | The shader samples from the centre of a tile's first texel to the centre of its last. The 1-texel gutter repeated by `RenderGradient` lies inside that range, not outside it, so it gives no protection against the next tile. |
| Gradients are not smooth | The position along a gradient comes from a 512×512 lookup texture ("gradient shape texture") with 8 bits per channel: only 256 distinct positions, so large gradients show steps. |
| Shimmering on small objects | The lookup texture has no mipmaps (despite trilinear filtering), so it aliases under minification, which is typical on phone screens. |
| A seam in conical gradients | The angle stored in the lookup texture wraps from 255 to 0, and bilinear filtering blends across the wrap. |
| Wrong gradients in large scenes | The atlas is a fixed 512×512 texture (512 gradients). Materials only reference the first atlas texture, so further gradients sample outside it. |

Vertex compression is not a cause: Unity 6's default mask (`VertexChannelCompressionMask: 4054`) compresses TexCoord1, which holds the gradient index, to 16-bit floats, but integers below 2048 stay exact.

**New design:**

The gradient *shape* (where a pixel lies along the gradient) becomes maths instead of a lookup texture, and colours are evaluated exactly from the gradient's stops. This follows how Chromium renders gradients through Skia: `t` is computed per pixel, the colour is evaluated analytically from the stops, and geometry never depends on gradients. Skia's only blurred path, a rasterised ramp texture, is the one we avoid.

1. **Linear gradients use vertex colours where a shape's triangles allow it.** Gradients never add tessellation: triangles come only from the shape.
   - Across a triangle, `t` is an affine function of position, so its range is `[min, max]` of the `t` values at the three vertices. **A triangle is exact if that range lies inside one band**: between two neighbouring stops, or in the flat *pad* area before the first or after the last stop. Vertex colours, set to the gradient's colour at each vertex, then reproduce it exactly.
   - A triangle that crosses a stop may still be close enough. Inside the triangle, both the true colour and the interpolated colour are affine between stop lines, so the largest difference occurs where a stop line crosses a triangle edge (it is zero at the vertices). Evaluating both colours at those crossing points gives the exact maximum error. **A triangle passes if that error is at most a tolerance**, by default half an 8-bit step (0.5/255) per channel.
   - **The decision is per shape.** If all of a shape's triangles pass, the shape uses vertex colours and the solid-colour shaders, needs no texture read and no gradient index, and batches with solid shapes. Otherwise the whole shape takes the stop-data path below. Its `t` still costs nothing per pixel, because linear `t` interpolates exactly from the vertices; the only cost is evaluating the stops.
   - In practice, two-stop gradients whose gradient line spans the shape (`t` from 0 to 1, the usual export from Illustrator and Figma) use vertex colours. Gradients with many stops, or spreads that repeat across the shape, usually use stop data.
2. **Radial and conical gradients compute `t` analytically.** Each vertex stores its position in the gradient's normalised space (TexCoord0, 32-bit float). Gradient space is an affine transform of the shape, so interpolating it across a triangle is exact. The fragment shader computes `t` in full precision (`float`):
   - radial: `t = length(g)`, using the SVG focal-point formula when the focal point differs from the centre;
   - conical: `t = atan2(g.y, g.x) / 2π + 0.5`, per pixel, so there is no seam.

   The spread method (pad, reflect, repeat) is applied to `t` in the shader.
3. **Otherwise the colour is evaluated from the gradient's stops, stored in a shared data texture.** This is the approach of Skia's newer Graphite backend (`colorize_grad_tex` in `src/sksl/sksl_graphite_frag.sksl`).
   - **Layout:** one row per gradient in a single `RGBAHalf` texture. Each stop takes two texels: its colour (sRGB) and its offset. A row holds up to 64 stops (128 texels); gradients with more stops are resampled to 64 with an import warning. Offsets are normalised at import so that the first stop is at 0 and the last at 1; `t` outside that range is handled by the spread method.
   - **Reading:** with `Texture2D.Load` (`texelFetch`): integer coordinates, no filtering, no mipmaps, no sampler state. Colours can't bleed between gradients, and texture resolution doesn't limit sharpness: hard stops stay perfectly sharp at any size.
   - **Evaluation:** find the interval containing `t`, then blend its two colours. Two-stop gradients read just their two colours. With more stops, a binary search reads log₂(N) offsets, then the interval's two colours and two offsets. All reads come from a tiny texture that stays in cache.
   - **Precision:** offsets are 16-bit floats, so an offset is accurate to about 0.0005. That's under half a pixel on a gradient 1,000 pixels long. `t` and the blend are computed in full precision (`float`), which OpenGL ES 3.0 and newer guarantee in fragment shaders.
   - **Memory:** 64 slots to start (256 KB), doubling as needed up to 4,096 gradients. Gradients that draw the same share a slot: they are compared exactly by their merged stops (`GradientKey`), not by a rounded text hash; the spread method joins the key when it is stored in the slot.
   - **Lifecycle:** the atlas is a cache that can be discarded and rebuilt at any time. Gradients aren't removed while an atlas exists, so a slot never changes meaning; a full atlas grows, and only an atlas that can't grow is replaced. Everything built from it (an asset's mesh with slot numbers, renderer meshes and materials) records the atlas generation it was built for. Script reloads destroy the atlas and those objects, and renderers rebuild in `OnEnable`; within a session, renderers register with the atlas and rebuild when it is replaced or their asset is reimported. `Assets/Tests/Editor/AtlasLifecycleTests.cs` checks that a scene renders the same across script reloads, play mode (with and without domain reload), reimports, a full atlas, scene switches and edits.
   - **Why not per-material uniforms** (Skia's `colorize_grad_4`/`_8` tiers): Skia sets uniforms per draw. Here, one material per gradient would split an SVG mesh into a draw call per gradient, and interleaving them with solid shapes in painter's order would multiply the draw calls. The shared data texture keeps one material and one draw per mesh.
4. **The gradient row is an exact integer per vertex.** TexCoord1 holds the row index (x) and the gradient type, spread and stop count packed into one integer (y). Both stay below 2,048, so they are exact even when Unity compresses the channel to 16 bits (Unity 6's default vertex compression mask, 4054, includes TexCoord1).
5. **Colours match browsers.** SVG interpolates colours in sRGB. Stop colours are stored as sRGB values and blended in sRGB, in the shader for stop data and by the GPU's interpolation for vertex colours. The result is then converted to linear in the *fragment* shader when the project uses Linear colour space. This costs a few arithmetic instructions per pixel and replaces the per-vertex conversion added in 2.0.
6. **Optional dithering**, as Chrome does for gradients. A material keyword adds ±½ of one 8-bit step of noise per pixel, from interleaved gradient noise computed from the screen position: pure arithmetic, with no lookup texture. It removes the banding that 8-bit output shows on long, subtle gradients.

**Cost per pixel compared with today** (stop-data reads are point reads from a tiny, cached texture):

| | Today | New |
|---|---|---|
| Linear | 2 dependent texture reads | none (vertex colour); if the shape fails the test, stop data as below |
| Radial | 2 dependent texture reads | `length()` + 2 point reads for 2 stops, about log₂(N) + 4 for N stops |
| Conical | 2 dependent texture reads | `atan2()` + the same reads as radial |

The native core (phase 2) outputs the same data: per-vertex `t` or gradient-space positions, and the importer makes the same per-shape decision. This part of the design therefore doesn't change when the core is replaced.

**Compatibility:** the mesh data changes, so the importer version is bumped and every `.svg` file reimports automatically. SVG Assets stored as `.asset` files (1.x) keep the old encoding until they are reimported; the SVG Asset Inspector offers *Reimport*, and converting them to `.svg` files (section 7) updates them too. The old shaders and the gradient shape texture are removed.

**Tests:**
- Linear gradients with two stops, many stops, hard stops and every spread method: rendered colours match the expected value at sample points, whichever path the shape takes. The per-shape decision is checked directly: two-stop gradients spanning the shape must use vertex colours.
- Neighbouring gradients with contrasting colours, in adjacent texture rows, sampled at `t` = 0 and 1: no bleeding.
- Hard stops on very large gradients stay sharp (a one-pixel transition).
- Smoothness: along a large gradient, adjacent pixels may differ by at most a small amount, so steps are caught.
- Focal radial gradients and the conical seam.
- Data texture growth past 64 and 1,024 gradients; gradients with more than 64 stops.
- Colours in Gamma and Linear projects match a browser rendering of the same SVG.
- Mobile precision: the same render tests with TexCoord channels forced to 16-bit floats, to emulate devices. Then on Android (Mali and Adreno GPUs) and iOS with the phase 1 test app.

### 7.2 Antialiasing

SVG Importer antialiases edges with geometry: a thin skirt (fringe) around each shape that fades to transparent, extruded to a fixed width in screen space by the vertex shader. The idea is sound, and it's how NanoVG and Skia antialias convex paths. The current implementation has these problems:

| Symptom | Cause |
|---|---|
| Spikes at sharp corners | `SVGMeshUtils.VectorLine` places each corner's outer vertex at the intersection of the two offset edges, which is a miter. Its length grows with 1/sin(θ/2), so sharp corners shoot out, and a corner is never split into a bevel. |
| Shapes look bolder and soft details smear | The skirt only grows outwards: full opacity on the true edge, transparent one width further out. Every antialiased shape is about half a pixel larger than it should be. |
| Wrong skirt width when an object is scaled unevenly or rotated in 3D | The shader extrudes along the object-space normal and scales it by the length of the object's x axis (orthographic) or the distance to the camera (perspective). Neither accounts for non-uniform scale, and the normal isn't transformed to screen space. |
| Edges too soft or too hard | Coverage is the vertex alpha interpolated across the skirt. That's only correct when the skirt ends up exactly one pixel wide. |
| Hairline seams between touching shapes | Each shape blends its own partial coverage over the previous result, so a pixel on an edge shared by two shapes lets the background show through ("conflation"). Skia, and therefore Chrome, has the same behaviour with per-shape antialiasing. MSAA avoids it, because each sample belongs to one shape. |

**New design.** It follows NanoVG's fill fringe and lyon's stroke tessellator; the width and coverage move to the GPU.

1. **The fringe is a 1-pixel stroke centred on the outline**, half inside the shape and half outside. Its inner edge is also the fill's edge, so shapes keep their true size.
   - The fringe is generated by lyon's stroke tessellator on each contour of the shape (outer contours and holes). lyon handles degenerate input such as zero-length segments, coincident points and 180° turns.
   - lyon's `StrokeVertex::normal()` is scaled so that moving a vertex along it widens the stroke by exactly 1 on each side. The width can therefore be chosen in the vertex shader, while the join geometry stays correct.
2. **Corners split into bevels when they get sharp.** Joins are miters up to a miter limit of 2 (corners down to about 60°) and bevels beyond it: the corner splits into one vertex per edge normal, plus a triangle that fills the outer gap. On the inside of a corner the fringe uses a single point, clamped as NanoVG's inner bevel does when segments are shorter than the fringe. The miter limit is a ratio, so the decision doesn't depend on the fringe width and can be made at import.
3. **The fill's boundary moves in by half a pixel in the vertex shader.** Fill vertices on the outline carry the same extrusion data as the fringe's inner vertices and are moved inwards by the same computation, so the fill and fringe meet exactly with no gap or overlap. This matters for semi-transparent fills, which would otherwise be blended twice under the fringe. Interior vertices have no extrusion and stay put.
4. **The width is computed in true screen pixels.** For a vertex at position `p` with extrusion `n` (object space), the vertex shader projects both `p` and `p + n·ε` through the full model-view-projection matrix. The difference gives the extrusion's direction and scale in screen pixels, and the vertex moves ±½ pixel (scaled by the miter factor) in clip space, multiplied by `w` so that it stays correct under perspective. This replaces today's per-axis scale heuristics and works for rotation, non-uniform scale, perspective and UI canvases.
   - Limitation: under strong non-uniform scale, a miter computed in object space isn't the exact miter in screen space. Sharp corners are bevels, so the error stays small.
5. **Coverage is computed per pixel.** Each fringe vertex carries its signed distance from the edge in pixels (−½ on the inner side, +½ on the outer side). The fragment shader computes coverage as `saturate(0.5 − d)`, a box filter one pixel wide. When the fringe is distorted, `fwidth(d)` rescales it, so edges stay one pixel soft. Derivatives are core in OpenGL ES 3.0.
6. **Thin shapes and strokes keep their weight.** Parts narrower than a pixel get folded fringes. SVG strokes narrower than one pixel on screen are drawn one pixel wide, with opacity scaled by their real width, as Skia does for hairlines. This prevents thin lines from flickering or vanishing when zoomed out.
7. **Antialiasing setting.** Per asset: *None*, *Geometry* (this section) or *Hardware*. *Hardware* emits no fringe and relies on the camera's MSAA. It's the best choice for illustrations made of many touching shapes (it has no seams) and saves the fringe's vertices and overdraw.
   - On mobile GPUs, MSAA is resolved on the chip. Meta measured 4x MSAA as extremely cheap on Quest; Arm's guidance is to avoid storing multisampled buffers to memory, which URP already does.
   - In *Geometry* mode, a later step (phase 3) can also omit the fringe on edges that two neighbouring shapes share exactly, which removes most seams in exported illustrations without MSAA. The native core finds such edges by hashing segment endpoints after flattening.

Fringes are always drawn with blending. In the *Opaque* format, they go into the transparent queue after the opaque fill.

**Mesh data per fringe vertex:** position on the path (`p`), extrusion vector (`n`, miter-scaled) and side (±1). The fill's boundary vertices get the same values. These replace today's `SVGShape.angles`. The native core produces them directly from lyon (phase 2); until then, 2.x keeps the current skirt.

**Tests:**
- Corners from 179° down to 1°: no rendered pixel lies further than one pixel outside the shape's bounds (no spikes), and corners are bevelled below the miter limit.
- Edge profile: across a straight edge at known sub-pixel offsets, pixel coverage matches a box filter within a few 8-bit steps, compared against resvg's analytic antialiasing on the same file.
- Shape size: an antialiased square covers the same total coverage as its true area, so it doesn't grow.
- Transforms: rotation, non-uniform scale, perspective and UI canvas scaling keep a one-pixel fringe.
- Semi-transparent fills: no darker band where fill and fringe meet.
- Thin strokes: a 0.25-pixel stroke renders as one pixel at about 25% opacity at every zoom level.
- Touching shapes: hairline seams are absent with *Hardware*, and with shared-edge detection in *Geometry*.

## 8. Runtime import

`SVGAsset.Load(string)` imports an SVG in a player build. It uses the same native core as the Editor, so runtime and Editor imports give the same result.

- **Supported** on the five targets in section 3: Windows, Linux and macOS standalone players, iOS and Android.
- **Not supported** on other platforms (WebGL, consoles, 32-bit Android). There, `SVGAsset.Load` throws `PlatformNotSupportedException`, and `SVGAsset.isRuntimeImportSupported` lets games check first.
- **The legacy C# parser is removed** together with the legacy import engine (phase 4). That removes a second implementation with different results.
- **Mobile limits:** runtime import uses the same input limits as the Editor (6.6), plus a configurable vertex budget, so a large file can't stall a phone.

## 9. Build and distribution

- **Location:** `native/` at the repository root, outside the package, as a Cargo workspace: `svgimporter-core` plus a `svgimporter-cli` for testing and benchmarks without Unity.
- **CI:** GitHub Actions builds the five targets on three runners: Windows (x64), Linux (x64 and Android arm64, using the Android NDK and `cargo-ndk`), and macOS (both macOS architectures, merged into one universal library with `lipo`, and iOS arm64). It runs the Rust tests, the conformance corpus and fuzzing smoke tests, checks that the generated C# bindings are up to date, then uploads the binaries.
- **iOS:** built as a static library (`crate-type = ["staticlib"]`), because iOS apps link native code statically. Unity links it into the Xcode project; the C# side imports from `__Internal`.
- **Android:** built as a shared library for `arm64-v8a`, linked with 16 KB page alignment (`-Wl,-z,max-page-size=16384`), which Google Play requires for apps targeting Android 15 and later.
- **Release:** a workflow copies the CI binaries into `Packages/com.jaroslavstehlik.svgimporter/Runtime/Plugins/` and opens a pull request. The binaries live in git, so installing from a git URL keeps working without a build step. The package is exempt from Git LFS (see `.gitattributes`), so they are stored as regular git objects.
- **Signing: none for now.** The libraries ship unsigned, to avoid paid Apple and Windows certificates.
  - macOS: a library installed by the Package Manager from git doesn't get the quarantine flag that browsers add to downloads, so the Editor loads it. Users who download a zip in a browser may see a Gatekeeper warning; the documentation explains how to allow the library (`xattr -d com.apple.quarantine`, or System Settings > Privacy & Security).
  - Windows: Unity loads unsigned DLLs; SmartScreen applies to downloaded executables, not DLLs.
  - iOS and Android: native libraries inside a package aren't signed; they're covered by the game's own app signing. Testing on devices is free (Android debug keys; Xcode's Personal Team for iOS, with 7-day provisioning).
  - Signing can be added later without design changes.
- **Size:** we expect a few MB per platform. To be confirmed in phase 1, using `opt-level="s"`, LTO and stripping. On mobile this adds to the app size, so text support (the largest dependency) is a Cargo feature that can be left out of the mobile builds if it turns out to be large.

Phase G, step 1 (2026-10-25): the gradient shaders compute the position along the gradient (linear, radial and conical) from the interpolated gradient coordinates instead of reading the 8-bit 512×512 gradient shape texture, which is removed. This fixes the blocky, stepped radial gradients visible when zoomed in and the seam of conical gradients, and saves one dependent texture read per pixel; the mesh data is unchanged, so nothing needs reimporting. Step 2: gradients are dithered (7.1, item 6), always on as in Chrome rather than behind a keyword: the noise is scaled by the blending alpha, so semi-transparent gradients get half a step after blending too, and added in sRGB in Linear projects. Step 3: stop data (7.1, item 3) in the existing atlas slots: each gradient's 128×4 slot holds its stops (colour and offset, two texels each, up to 64) and the stop count, in an `RGBAHalf` texture read with `Load`; shaders binary-search the stops and interpolate in sRGB, then convert to linear in Linear projects (item 5). The mesh data and slot indices are unchanged; the growable one-row-per-gradient texture and the packed TexCoord1 (item 4) can follow when spread methods need the extra data. The resvg hard-stop tests now pass (native 860 of 1,748). Step 4: spread methods and focal points. They are stored in the gradient's slot (row 1: stop count, spread, focal offset, then focal radius) rather than packed into TexCoord1, so the mesh data stays the same; `GradientKey` includes them, so gradients that differ only in spread or focal point get separate slots. Radial gradients are two-point conical gradients, as in SVG 2: the shader solves for the largest circle between the focal circle and the end circle that passes through the pixel, and pixels no circle reaches are not painted. All 87 resvg linear and radial gradient tests pass with the native engine. Vertex colours for linear gradients (item 1) remain.

**Import pipeline (2026-10-25).** `SVGImport.Import(svgText, SVGImportOptions)` is the one import: the Editor importer, `SVGAsset.Load` and 1.x `.asset` SVG Assets call it and write its `SVGImportResult` to the asset with `SVGAsset.Apply`. An engine produces layers and outlines into a per-import context (the native adapter directly; the legacy parser through its static fields, set and cleared around the call); shared steps then place them on the canvas, build the mesh, choose shaders and gather gradients and the collider. Results are keyed by a hash of the text and options instead of a time stamp, diagnostics travel in the result and are logged by the importer, and failures produce an error result without touching the asset. Tested by `Assets/Tests/Editor/ImportTests.cs`.

Phase A, step 1 (2026-10-25): the native core builds the fringe (`native/svgimporter-core/src/fringe.rs`) as a layer of kind `SVGI_LAYER_FRINGE` after each fill and stroke, with per-vertex extrusion vectors and coverage in the result (ABI 3), so the Native engine uses no C# mesh code. The Legacy engine, still the default outside macOS, gets the same fringe from a C# port (`SVGFringe`) until it is removed in phase 4. Both are built directly from the outline with the same small algorithm, rather than with lyon's stroke tessellator, so the two engines produce identical fringes; lyon can replace it once the Legacy engine is gone. It follows 7.2 items 1 to 5 with one simplification: coverage is the vertex alpha interpolated across the fringe, which is exactly the box filter of item 5 because the vertex shader makes the fringe exactly the antialiasing width on screen; a separate per-pixel distance isn't needed. Each fringe vertex lies on the outline and carries its extrusion vector (outward for the transparent edge, inward for the opaque one, miter-scaled) in NORMAL; fill vertices on the outline carry the inward vector, so fill and fringe meet exactly. Corners are miters up to a miter limit of 2 and bevels beyond. The vertex shader differentiates the projection to get pixels per object unit along the vector, so the width is right under any transform. `Assets/Tests/Editor/AntialiasingTests.cs` checks size, the edge profile, holes, sharp corners, double blending and a rotated, stretched object, for both engines; the old fringe fails four of the seven checks. Unity's default vertex compression stores NORMAL, and TexCoord1, as 16-bit floats, which is ample for extrusion vectors up to 2; TexCoord0, which holds the gradient coordinates, isn't compressed (mask 4054 leaves out UV0). Still to do: thin strokes (item 6). Instead of a *Hardware* option (item 7), which would suggest the plugin turns MSAA on, the setting is named **Soft Edges** in the Editor, with a tooltip and a hint when it's off saying that MSAA is a camera setting; MSAA-only rendering is Soft Edges off plus MSAA on the camera. Thin strokes are deferred; the plan: the importer stores each stroke outline vertex's stroke width along its extrusion direction (from `stroke-width` and the transforms, known to both engines) in TexCoord2, and the vertex shader, which already computes pixels per object unit along that direction, draws strokes narrower than a pixel one pixel wide with their opacity scaled by the true width, as Skia does. Thin fills would need their local thickness measured at import and stay out of scope.

Phases G, 5 and 6 don't depend on the native core and can start right away. G is C# and shader work, and can ship as 2.1. Phase A needs lyon's fringe data and follows phase 2; its *Hardware* option can ship earlier. Phase L is shader work and can also start now. Phase O is C# and shader work and can ship in 2.x. Phase F needs the fringe from phase A. Phase R needs resvg and follows phase 3; phase I can start with solid fills and grow with them.

## 15. Decisions and open questions

Decided:
- Targets: Windows x64, Linux x64, macOS universal (arm64 + x64), iOS arm64, Android arm64 (section 3).
- Runtime import uses the native core on those targets; the legacy C# parser is removed (section 8).
- C# bindings are generated with csbindgen (6.3).
- Every cost beyond one mesh, one shared material and one batched draw is opt-in and shown in the Inspector (goal 6).
- In Linear colour space projects, soft edges (antialiasing, blur) and semi-transparent shapes blend in linear light, as everything else in Unity does. They are not adjusted to match browsers, which blend in sRGB; the documentation explains the difference (section 16, item 4).
- Antialiasing uses a fringe centred on the edge with bevelled sharp corners, extruded in screen pixels in the vertex shader and with coverage computed per pixel; MSAA is offered as an alternative (7.2). Coverage uses the distance to the nearest edge, as Skia's GPU convex-path renderer does. Exact-area coverage (Skia's CPU "analytic AA") was rejected: it only improves sharp corners and sub-pixel details and needs compute or CPU work per frame.
- Gradient shapes are computed, not looked up, and colours are evaluated exactly from stops kept in a shared data texture, as in Skia/Chromium. Gradients never add tessellation. Linear gradients use vertex colours when every triangle of the shape passes an exact error test (7.1).

- Libraries ship unsigned for now (section 9).
- Fonts get no special handling: text uses usvg's default system fonts in the Editor, and runtime import skips text.
- `svgimporter-cli` stays internal: it is used to test and benchmark the core without Unity, and can be published later.

## 16. Gaps and future work

Compared with other SVG solutions, the design above gives SVG Importer browser-grade parsing (usvg), Skia-grade gradients and antialiasing, and the lowest runtime cost on mobile: baked meshes, one batched draw per SVG and an opaque mode that reduces overdraw. Unity's own Vector Graphics package supports only a subset of SVG 1.1 (no text, masks or filters) and is labelled experimental; Godot rasterizes SVG to textures with ThorVG. The gaps below decide whether real-world files and normal Unity 2D workflows work without surprises. Items 1–5 are part of the plan; items 6–11 are candidates after 3.0.

### Important

**1. Unity integration.** Today an SVG Asset renders only through SVG Importer's own `SVGRenderer` and `SVGImage`. It doesn't work with SpriteRenderer, Sprite Atlas, 2D Animation (bones), Sprite Shape, Tilemap or UI Toolkit, all of which Unity's Vector Graphics package targets.
- **Sprites:** add an import target that produces a mesh Sprite with vertex colours, as Unity's *Vector Sprite* does. To investigate: which vertex attributes Sprites can carry (`SpriteDataAccessExtensions.SetVertexAttribute`), which decides whether gradients beyond the vertex-colour path work. If they can't, those shapes fall back to the raster fallback (item 5).
- **UI Toolkit:** render SVG Assets in a custom `VisualElement` through `generateVisualContent` (`MeshGenerationContext`), which is public API. UI Toolkit doesn't take custom shaders, so solid fills and vertex-colour linear gradients work directly; other gradients need the raster fallback. To investigate: whether a UI Toolkit `VectorImage` can be produced through public API, so SVGs can be used as element backgrounds in UI Builder.

**2. 2D lighting.** With the URP 2D Renderer, SVG shapes are drawn unlit (section 7.2's `Universal2D` pass), so 2D lights, shadows and normal maps don't affect them. Add *SVG Lit (2D)* shaders whose `Universal2D` pass samples URP's 2D light textures, as URP's `Sprite-Lit-Default` does. Normal maps come from the generated normals. The pass uses URP include files, so it sits in a SubShader with a `PackageRequirements` block and projects without URP still compile. This is shader work and doesn't need the native core.

**3. Group opacity.** `opacity` on a group applies to the group's combined result: browsers and Skia render the group into an offscreen layer (`saveLayer`) and composite that with the opacity. SVG Importer applies it to each child instead, so where children overlap, lower children show through upper ones. Group opacity in SVG files is common in exports from Illustrator and Figma, and the main place it matters is UI (uGUI).

Cutting overlapping children apart at import was considered and rejected: every cut adds the upper shape's outline to the shape below, which multiplies vertices in layered artwork, and the cut pieces show seams along every cut once they are antialiased.

The design:
- **At import, record whether each group with opacity has overlapping children** (a cheap polygon-overlap test with Clipper, later `i_overlay`). If none overlap, opacity per child is exact and nothing else is needed. This is the common case for icons.
- **The default stays free: opacity per child.** Following goal 6, accurate group opacity is an opt-in, because both methods below cost something. When an asset has a group whose children overlap, the Inspector says that its opacity is applied per shape and offers the accurate setting with its cost.
- **uGUI (`SVGImage`), opt-in "Accurate Group Opacity": a cached offscreen layer.** It costs a render target and breaks batching with neighbouring UI elements for as long as it's active. When enabled and the asset contains a group whose opacity needs compositing, `SVGImage` renders its whole mesh once into a pooled `RenderTexture` the size of its rectangle on screen, through a command buffer executed immediately (this works the same in every render pipeline), and then draws a single quad with that texture.
  - It is exact: it is the offscreen layer, with any nesting of groups, antialiasing, gradients and semi-transparency. It adds no vertices and no seams.
  - The texture is re-rendered only when something visible changes: the element's size or the canvas scale (so it stays sharp), its colour, its asset, or a modifier. Otherwise it costs one textured quad per frame.
  - Memory: one texture per visible element that needs it, at its on-screen size, for example 64 KB for a 128×128 icon or about 8 MB for a full-screen 1920×1080 illustration. The Inspector shows when an asset needs compositing and why.
  - Rendering into the transparent texture uses premultiplied alpha, so edges composite correctly.
  - A separate opt-in, "Accurate Fade", uses the same path to make runtime fades exact. While a `CanvasGroup` or the element's colour makes it translucent, `SVGImage` uses the cached texture even for assets without group opacity, and releases it when alpha returns to 1. `UIBehaviour.OnCanvasGroupChanged` tells it when that happens.
- **World space (`SVGRenderer`), opt-in: depth.** It costs one extra depth-only draw per group. For an overlapping group, a depth-only pass first draws the group's fills, each child at its own depth with upper children closer; then the fills are drawn with depth test *Equal* and the group's opacity, so each pixel takes only its topmost child; finally the fringes are drawn with depth test *LessEqual*. It adds no vertices and leaves no seams. The only inexactness is in the one-pixel fringe on internal edges: c·α·(1−α)·(A − background), at most about 12 % of the colour difference at α = 0.5. Where no depth buffer is available, `SVGRenderer` can use the cached-layer path as well.
- **Exact rasterization at import (item 5)** stays available per asset, for content that also uses filters or masks.

**4. Blur and drop shadows as feathered geometry.** Gaussian blurs on shapes and drop shadows (an offset, blurred copy of a shape) are the most common SVG filters in exports. Following Rive's "feathering", they become geometry instead of rasterized images: the antialiasing fringe (section 7.2) is widened to the blur's radius, and its coverage profile changes from a one-pixel box to the integral of a normal distribution (`erf`), centred on the path's edge. The result is resolution-independent and stays in the same mesh, material and draw call, so it's on by default.
- Rive reports results visually identical to a Gaussian blur on a rasterized image, and describes a 2D correction for curves and corners, where curvature shifts the 50 % point. Rive doesn't publish that formula, so a first version uses the straight-edge profile and accepts slightly softer corners.
- Only blurs and shadows of shapes qualify. Filter chains that combine images, or blur whole groups with overlapping content, use the raster fallback.
- Source: https://rive.app/blog/how-rive-reinvented-feathering-for-the-vectorian-era
- **Prototype** (`Assets/Prototypes/FeatheredShapes`): rectangles and rounded rectangles, compared with Chrome's `feGaussianBlur` rendering of the same SVG at the same pixel size. Rectangles are exact (a product of two `erf` integrals). Rounded rectangles integrate `erf` across 8 horizontal slices, each weighted by its exact Gaussian mass, within 4σ. In Gamma colour space the difference from Chrome is at most 4/255 (mean 0.4/255) for σ = 12, including a 20-pixel-wide rectangle, which the straight-edge profile can't handle. A drop shadow under a crisp card differs by up to 27/255 only along the card's crisp edge, where Chrome's antialiasing differs from a σ = 0.4 px Gaussian. The same function with σ ≈ 0.4 px draws antialiased shapes, so blur and antialiasing are one continuous effect.
- **Linear colour space differs from browsers for every soft edge.** Browsers blend in sRGB. A Unity project in Linear colour space blends in linear light, so the same coverage produces lighter dark-on-light edges: the prototype in Linear differs from Chrome by up to 76/255 in blurred regions. This affects blur, antialiasing and semi-transparent shapes alike. **Decision:** keep Unity's standard linear blending and document the difference; SVG Importer doesn't try to emulate browser (sRGB) blending.

**5. Raster fallback, opt-in, for what can't become geometry**: filters other than item 4, masks that aren't simple clips, blend modes, embedded images and patterns. resvg, from the same project as usvg, rasterizes just those groups at import into a mipmapped texture stored in the SVG Asset. The texture is placed in the mesh as a textured quad, in painter's order (`FILL_TYPE.TEXTURE` already exists). The resolution is an import setting, and these parts are no longer resolution-independent; the Inspector shows which elements were rasterized and why. Each asset with rasterized parts needs one extra material, so one more draw call, plus the texture memory. Following goal 6, it is off by default: unsupported elements are skipped, and the Inspector lists them and offers the fallback with its cost.

### Candidates after 3.0

**6. Quality at high zoom.** Curves are flattened at import with a tolerance from the *Quality* setting, so extreme zoom shows facets. Options:
- **Levels of detail:** several tolerances per asset, with `SVGRenderer` choosing by screen size.
- **Exact curves on the GPU** (Loop–Blinn): the triangles along curved edges carry curve coordinates, and the fragment shader computes coverage against the true curve. This is exact at any zoom, but it's significant work.

**7. Stroke width at runtime.** Strokes from lyon carry the same normals as the antialiasing fringe, so their width can also be applied in the vertex shader. That enables SVG's `vector-effect: non-scaling-stroke` and animatable stroke widths.

**8. Text as text.** Text is converted to curves, so it can't be edited or localized. An import option could map simple `<text>` elements to TextMeshPro objects, keeping the rest as geometry.

**9. Colour.** CSS Color 4 interpolation spaces (for example oklab), the `color-interpolation` property, and wide-gamut colours.

**10. Interaction.** Hit-testing and events per SVG element: layers already keep element ids and bounds, but there is no API to ask which element is under a point.

**11. Performance work.** Confirm SRP Batcher compatibility with the Frame Debugger, cull layers of large documents by their bounds, and use smaller vertex formats where precision allows.

### Out of scope

SVG animation (SMIL and CSS), and the vector animation formats used in practice today, Lottie and Rive. SVG Importer animates through its own components (frame animator, modifiers) and Unity's animation system.
