# SVG Importer 3: Native Import Core

Status: proposal · Owner: Jaroslav Stehlík · Last updated: 2026-10-24

This document plans the next modernisation step of SVG Importer: replacing the C# SVG parser and tessellator with established native libraries, while keeping the Unity side (importer, Inspector, render formats, modifiers) in C#. It also plans the samples and the documentation.

Version 2.0 (the `modern` branch) already made the plugin a UPM package for Unity 6 with URP support and a `ScriptedImporter`. This plan builds on that.

## 1. Goals

1. **Parse SVG robustly.** Real-world files from Illustrator, Inkscape, Figma, Affinity and browsers should import correctly, including CSS, `<use>`/`<symbol>`, nested transforms, gradients in both unit systems, clip paths and text.
2. **Tessellate robustly and fast.** Correct fills for any path (self-intersections, holes, both fill rules), proper strokes (joins, caps, miter limits, dashes), no cracks, no crashes.
3. **Keep everything Unity-specific in C#.** The Inspector, the render formats (Opaque, Transparent, uGUI), depth handling, the gradient atlas, layers for modifiers, colliders and serialization stay as they are, so existing projects and APIs keep working.
4. **Measure quality.** A conformance corpus with reference images gives a support percentage that we track over time, instead of discovering failures from user reports.
5. **Ship samples as Unity samples and documentation as package documentation.**

### Non-goals

- Rendering SVG at runtime with a vector renderer. SVG Importer bakes meshes at import time; that is its main advantage on mobile.
- Supporting SVG features that cannot become a mesh: filter effects, blending modes and, in general, luminance masks. They are reported as warnings.
- Changing the runtime data model (`SVGAsset`, `SVGLayer`, `SVGShape`) beyond additions.

## 2. Today

```
.svg ─► C# XML parser (SmallXmlParser) ─► C# SVG DOM ─► C# path flattening
     ─► Clipper (C#) + LibTessDotNet (C#) ─► SVGLayer[] / SVGShape[]
     ─► SVGMesh.CombineMeshes (format, depth, gradients) ─► SVGAsset (Mesh, shaders, gradients, layers, collider)
```

The pipeline after `SVGLayer[]` is Unity-specific and works well. The part before it is the problem:

- The parser is a hand-written partial SVG 1.1 implementation from 2015. Recent fixes (gradient units, radial radius) show how much of the spec is approximated. CSS support is minimal and there is no text support.
- Tessellation uses LibTessDotNet, a C# port of SGI libtess. It is robust but slow, and strokes are generated by custom code.
- There is no test corpus. Support is described by a feature list in the README, not measured.

## 3. Targets

Meshes are baked at import time, so most of the work happens in the Unity Editor. The core also runs in players, so that `SVGAsset.Load` can import SVG at runtime on devices (section 8).

| Target | Rust target | Library | Used by |
|---|---|---|---|
| Windows x64 | `x86_64-pc-windows-msvc` | `svgimporter_core.dll` | Editor, standalone player |
| Linux x64 | `x86_64-unknown-linux-gnu` | `libsvgimporter_core.so` | Editor, standalone player |
| macOS arm64 | `aarch64-apple-darwin` | `libsvgimporter_core.dylib` | Editor, standalone player |
| iOS arm64 | `aarch64-apple-ios` | `libsvgimporter_core.a` (static) | Player |
| Android arm64 | `aarch64-linux-android` | `libsvgimporter_core.so` | Player |

Not targeted: Intel Macs, Windows and Linux on arm64, 32-bit Android (armv7), WebGL and consoles. On these platforms, importing in the Editor isn't available (the importer reports a clear error), and players use the meshes baked at import time, as they always have. Only runtime import is unavailable there (section 8).

## 4. Library selection

### 4.1 Parser

| Library | Language | License | Notes |
|---|---|---|---|
| **usvg** (resvg project) | Rust | Apache-2.0 OR MIT | Parses SVG into a simplified, fully resolved tree: shapes become paths, styles and CSS are resolved, `<use>` and `<symbol>` are expanded, and text can be converted to paths with real fonts. It comes from the resvg project, which maintains a large SVG test suite with a published support table comparing it to browsers. It is actively maintained (v0.49.0 released 2026-10-24) and has about 4,100 GitHub stars. |
| ThorVG | C++ | MIT | Complete vector engine with SVG and Lottie loaders, used by Godot and Tizen. Its tessellator is internal to the GL renderer, not a separate API, and the loader is tied to its scene graph. |
| LunaSVG / PlutoSVG | C++ / C | MIT | Built for rendering to bitmaps. Smaller community, less complete CSS. |
| NanoSVG | C | Zlib | Single header, tiny and fast, but deliberately minimal: no CSS cascade, no text, limited `<use>`. Not robust enough for arbitrary files. |
| librsvg | Rust/C | LGPL-2.1 | Very complete, but the LGPL license and the cairo/glib dependency chain don't suit a redistributed Unity plugin. |
| Unity Vector Graphics | C# | Unity Companion License | Unity's own importer. Bound to Unity's license and API, and we would compete with the importer it already provides. |

**Choice: usvg.** It does the hardest part of SVG, resolving the document, better than any other library with a friendly license. It outputs exactly what a tessellator needs: absolute paths with resolved paint and transforms. Its test suite also gives us a ready-made conformance corpus.

### 4.2 Tessellator

| Library | Language | License | Notes |
|---|---|---|---|
| **lyon** (`lyon_tessellation`) | Rust | MIT OR Apache-2.0 | Fill tessellator (sweep line, both fill rules, self-intersections) and stroke tessellator (joins, caps, miter limit, per-vertex normals). Flattening tolerance is configurable. Widely used in Rust graphics. Actively maintained: `lyon_tessellation` is at 1.0.23 and was updated 2026-10-23. |
| libtess2 | C | SGI Free B | What we use today, in its C# port. Robust, slower, fill only. |
| earcut | C++/C# | ISC | Very fast, but only for simple polygons with holes. It can't handle self-intersections or fill rules without pre-processing. |
| Clipper2 | C++/C# | BSL-1.0 | Polygon boolean operations, not a tessellator. A candidate for clip paths. |
| i_overlay | Rust | Apache-2.0 | Polygon boolean operations in Rust, a candidate for clip paths (see 6.4). |

**Choice: lyon**, with `i_overlay` (or Clipper2) for boolean operations. The parser and tessellator then share one language and one build. lyon's stroke tessellator also returns the per-vertex normals that our antialiasing fringe needs today (`SVGShape.angles`).

### 4.3 Why Rust, and not C# or C++

- **Robustness:** the core parses untrusted input. A crash in a native plugin takes down the Unity Editor. Safe Rust removes the memory-safety class of crashes, and panics can be caught at the boundary (6.6).
- **Speed:** native code is much faster than the current C# for both parsing and tessellation, which matters most for runtime import on phones. We will measure it rather than assume (phase 0 sets the baseline).
- **The best libraries are already Rust.** For C# we would have to port them, which is how we got the current state. For C++, ThorVG is the only comparable option, and its tessellator isn't exposed.
- **Portability cost is moderate:** five targets (section 3), all of which Rust supports in its top tiers. iOS and Android need a little extra build setup (section 9).

The cost is a Rust toolchain for contributors who change the core. Contributors who only change the Unity side need nothing new, because the binaries ship prebuilt in the package.

## 5. Architecture

```
 ┌───────────────────────────── native: svgimporter-core (Rust) ─────────────────────────────┐
 │  .svg bytes ─► usvg (parse, resolve CSS/use/units/transforms, text → paths)               │
 │            ─► clip paths: boolean ops (i_overlay)                                         │
 │            ─► fills: lyon FillTessellator      strokes: dash (tiny-skia-path) + lyon Stroke │
 │            ─► AA fringe: lyon stroke of the outline, with normals                          │
 │            ─► flat result buffers (layers, vertices, indices, paints, diagnostics)         │
 └──────────────────────────────────────── C ABI ────────────────────────────────────────────┘
 ┌──────────────────────── C#: SVGImporter.Runtime (+ Editor for the importer) ───────────────┐
 │  SVGNativeCore (P/Invoke, blittable structs) ─► SVGLayer[] / SVGShape[] / SVGFill          │
 │  ─► existing pipeline: SVGMesh.CombineMeshes (Opaque depth / Transparent order / uGUI),    │
 │     gradient atlas (CCGradient), collider shape, layers for modifiers                     │
 │  ─► SVGFileImporter ─► SVGAsset                                                            │
 └────────────────────────────────────────────────────────────────────────────────────────────┘
```

**The boundary is `SVGLayer[]`.** Everything downstream of it is Unity-specific and stays in C#, unchanged. The native core replaces only what produces the layers today. That keeps the change testable: for the same SVG, both paths produce layers that we can compare.

## 6. Native core

### 6.1 Pipeline

1. **Parse** with usvg. Options passed from C#: DPI, default font family, a font directory, and whether to convert text.
2. **Walk the tree** in document order. Each path that has a fill and/or a stroke produces one layer, in the order the shapes are painted. Groups pass their transform and opacity down. Each layer carries the element `id`, which modifiers and future per-layer features key on.
3. **Fill:** tessellate with lyon using the path's fill rule (`nonzero` or `evenodd`) and a tolerance derived from the import's *Quality* (vertices per meter) and *Scale* settings.
4. **Stroke:** apply the dash array with tiny-skia-path if there is one, then tessellate with lyon's stroke tessellator (width, joins, caps, miter limit).
5. **Clip paths:** intersect the flattened geometry with the clip path polygon before tessellation. For `clipPathUnits="objectBoundingBox"`, usvg provides the bounding box.
6. **Antialiasing:** if enabled, produce the fringe as a zero-width stroke of the shape outline, emitting lyon's per-vertex normals. This matches today's `SVGShapeType.ANTIALIASING` shapes, so the existing antialiased shaders keep working.
7. **Paint:** output solid colors, or gradient descriptions (linear/radial, spread method, stops, gradient-to-shape transform). C# turns these into the existing gradient atlas entries and UVs, exactly as today.
8. **Diagnostics:** report unsupported features (masks, filters, images, blend modes) with element ids, and parse errors with line numbers. These replace today's `SVGError` flags; the old flags stay for compatibility.

### 6.2 What stays in C#

- `SVGFileImporter` and the Inspector, with the same settings and field names.
- Render formats: Opaque (per-layer depth offsets, *Compress Depth*), Transparent (painter's order), uGUI.
- Gradient atlas and gradient UV encoding, shaders, materials and the URP/Built-in support.
- Layers for modifiers (*Use Layers*), collider generation, pivot, 9-slice border, mesh compression, normals and tangents.

### 6.3 C ABI

The ABI is a small set of blittable structs and three functions. Written in Rust, shown here as C:

```c
typedef struct { float dpi; float tolerance; uint8_t antialiasing; uint8_t convert_text; const char* font_dir; } SvgiOptions;

typedef struct {
    uint32_t vertex_offset, vertex_count;   // into vertices (float2) and normals (float2, AA only)
    uint32_t index_offset, index_count;     // into indices (uint32)
    uint32_t paint;                         // into paints
    uint8_t  kind;                          // 0 fill, 1 stroke, 2 antialiasing
    uint32_t name_offset, name_length;      // element id, UTF-8, into strings
} SvgiLayer;

typedef struct {
    uint8_t  type;                          // 0 solid, 1 linear, 2 radial
    float    color[4];                      // solid color, opacity applied
    float    transform[6];                  // gradient space to shape space
    float    x1, y1, x2, y2, r, fx, fy;     // gradient geometry
    uint8_t  spread;                        // pad, reflect, repeat
    uint32_t stop_offset, stop_count;       // into stops (offset + color)
} SvgiPaint;

int32_t  svgi_import(const uint8_t* svg, size_t length, const SvgiOptions* options, SvgiResult** result);
void     svgi_free(SvgiResult* result);
uint32_t svgi_version(void);
```

**The C# side is generated, not written by hand.** [csbindgen](https://github.com/Cysharp/csbindgen) (MIT, by Cysharp, built for .NET and Unity) runs in the core's `build.rs` and generates `NativeMethods.g.cs`: the `[DllImport]` declarations and matching `[StructLayout(LayoutKind.Sequential)]` structs. The generated file is committed in the package's Editor assembly, and CI fails if it differs from a fresh build, so the two sides can't drift apart. A thin hand-written `SVGNativeCore` class wraps the generated calls in safe C# (pinning input, copying results, freeing native memory, turning error codes into exceptions).

Alternatives considered:
- **interoptopus** (MIT) generates a richer, safer C# layer: services as disposable classes, slices, strings, and Rust `Result`s as exceptions. That would replace most of `SVGNativeCore`. However, its current C# backend (0.16) emits `[LibraryImport]` with `static partial` methods, which need .NET 7's interop source generator. Unity's Mono and IL2CPP don't have it, so the output doesn't compile in Unity. The Unity flavour from 0.10 onwards now lives in the project's `crates/_old` folder. Worth revisiting if a Unity/`DllImport` output returns, or if Unity moves to CoreCLR.
- **uniffi-bindgen-cs** (MPL-2.0) follows Mozilla's UniFFI model, which is a heavier fit for a three-function API.

All arrays live in one allocation owned by the native side. C# copies them into managed arrays in one pass and calls `svgi_free`. No callbacks, no state between calls, and no threading assumptions, so imports can run in parallel in Unity's import worker processes.

### 6.4 Clip paths and masks

- **Clip paths:** supported by polygon intersection before tessellation. This fixes today's "experimental" clip paths and the unsupported `objectBoundingBox` units.
- **Masks:** a mask whose content is a single opaque shape can become a clip path. Other masks can't be represented as geometry and produce a warning.

### 6.5 Text

usvg converts text to paths using fonts. In the Editor we pass the system font directories plus a project font folder from the settings. At runtime on devices, system fonts aren't reliably available, so runtime import only uses fonts the project ships (passed as font data), or skips text with a warning. Files that use fonts which aren't available fall back to a default font and produce a warning. This removes the current "convert text to curves" requirement in most cases.

### 6.6 Crash safety

- Every exported function wraps its body in `catch_unwind` and returns an error code instead of unwinding into C#.
- Guard against pathological input: limits on document size, nesting depth, `<use>` expansion and output vertex count. Exceeding a limit is a reported error, not a hang.
- Fuzz with `cargo-fuzz` in CI.

## 7. Integration in Unity

- **Plugin files:** `Runtime/Plugins/<platform>/` inside the package. Each library's import settings enable it for its OS and CPU only: for Editor and standalone on Windows, Linux and macOS, and for the player only on iOS and Android.
- **C# wrapper:** the generated `NativeMethods.g.cs` plus the hand-written `SVGNativeCore` in the `SVGImporter.Runtime` assembly, because players use it too. On iOS the library is linked statically, so the import name is `__Internal` there; csbindgen generates that switch. On platforms without a library, `SVGNativeCore.isSupported` is false. `SVGNativeCore` checks `svgi_version()` against the version it was built for and shows a clear error if the binary is missing or mismatched.
- **Converter:** a `SVGNativeConverter` (in the runtime assembly, shared by the importer and `SVGAsset.Load`) maps the result into `SVGLayer`/`SVGShape`/`SVGFill`. The existing `SVGMesh.CombineMeshes` then runs unchanged.
- **Engine setting:** during the transition, a project setting *Import Engine: Native / Legacy* selects the core. The importer version is bumped when the default changes, so every `.svg` reimports once. The legacy engine is removed after phase 3.
- **Legacy `.asset` SVG Assets:** unaffected. They keep their baked meshes and can still be reimported with the legacy engine until it is removed. The converter (`Window > SVG Importer > Convert SVG Assets to SVG Files`) moves them to the new path.

## 8. Runtime import

`SVGAsset.Load(string)` imports an SVG in a player build. It uses the same native core as the Editor, so runtime and Editor imports give the same result.

- **Supported** on the five targets in section 3: Windows, Linux and macOS standalone players, iOS and Android.
- **Not supported** on other platforms (WebGL, consoles, Intel Macs, 32-bit Android). There, `SVGAsset.Load` throws `PlatformNotSupportedException`, and `SVGAsset.isRuntimeImportSupported` lets games check first.
- **The legacy C# parser is removed** together with the legacy import engine (phase 4). That removes a second implementation with different results.
- **Mobile limits:** runtime import uses the same input limits as the Editor (6.6), plus a configurable vertex budget, so a large file can't stall a phone.

## 9. Build and distribution

- **Location:** `native/` at the repository root, outside the package, as a Cargo workspace: `svgimporter-core` plus a `svgimporter-cli` for testing and benchmarks without Unity.
- **CI:** GitHub Actions builds the five targets on three runners: Windows (x64), Linux (x64 and Android arm64, using the Android NDK and `cargo-ndk`), and macOS (macOS arm64 and iOS arm64). It runs the Rust tests, the conformance corpus and fuzzing smoke tests, checks that the generated C# bindings are up to date, then uploads the binaries.
- **iOS:** built as a static library (`crate-type = ["staticlib"]`), because iOS apps link native code statically. Unity links it into the Xcode project; the C# side imports from `__Internal`.
- **Android:** built as a shared library for `arm64-v8a`, linked with 16 KB page alignment (`-Wl,-z,max-page-size=16384`), which Google Play requires for apps targeting Android 15 and later.
- **Release:** a workflow copies the CI binaries into `Packages/com.jaroslavstehlik.svgimporter/Runtime/Plugins/` and opens a pull request. The binaries live in git, so installing from a git URL keeps working without a build step. The package is exempt from Git LFS (see `.gitattributes`), so they are stored as regular git objects.
- **Signing:** the macOS library is code-signed and notarized, and the Windows DLL is signed, so Gatekeeper and SmartScreen don't block the Editor from loading them. iOS and Android libraries are signed as part of the game's own app signing.
- **Size:** we expect a few MB per platform. To be confirmed in phase 1, using `opt-level="s"`, LTO and stripping. On mobile this adds to the app size, so text support (the largest dependency) is a Cargo feature that can be left out of the mobile builds if it turns out to be large.

## 10. Quality and testing

1. **Conformance corpus:** the resvg test suite (SVG files with reference PNGs, same license as resvg). A Unity test renders each file through the importer and compares it against the reference with a perceptual threshold. The result is published as a support table on the website, and CI fails on regressions.
2. **Real-world corpus:** exports from Illustrator, Inkscape, Figma and Affinity, plus the sample SVGs. They must import without errors.
3. **Existing render tests** (`Assets/Tests/Editor/SVGRenderTests.cs`): Built-in, URP and URP 2D, in Gamma and Linear. These must stay green.
4. **Samples:** every sample scene must render the same as with the legacy engine, within a small threshold for different triangulation.
5. **Benchmarks:** import time and peak memory for the sample set and the corpus, legacy vs native, tracked in CI.
6. **Layer parity:** for each corpus file, compare layer count, order and names against the legacy engine, to protect modifiers.

## 13. Phases

| Phase | Work | Done when |
|---|---|---|
| 0. Baseline | Add the resvg corpus and the Unity comparison test; benchmark the legacy engine | Legacy support percentage and import times are recorded |
| 1. Prototype | `svgimporter-core` with usvg + lyon fills and strokes, the C ABI and the CLI; build on all five targets | Corpus imports without crashes; native vs legacy speed is measured; a test app runs runtime import on an iPhone and an Android phone |
| 2. Integration | C# wrapper and converter to `SVGLayer[]`, gradients, AA fringe, *Import Engine* setting (default Legacy) | Render tests, samples and layer parity pass with the native engine |
| 3. Parity and beyond | Clip paths, dashes, text, masks-as-clips, diagnostics in the Inspector | Native support percentage ≥ legacy on every category; native becomes the default |
| 4. Release 3.0 | Signing, CI release pipeline, legacy C# engine removed | Clean install from git on Windows, Linux and macOS Editors; runtime import works in iOS and Android builds |
| 5. Samples | Focused samples from section 11 | All samples render in URP and Built-in |
| 6. Documentation | `Documentation~`, DocFX site, website link | Package Manager's *Documentation* link opens the site |

Phases 5 and 6 don't depend on the native core and can start right away.

## 14. Risks

| Risk | Mitigation |
|---|---|
| usvg's output loses information the modifiers rely on (for example group structure) | Phase 2 layer-parity test. usvg keeps groups and ids, so we can keep the existing layer granularity. |
| A native crash takes down the Editor | Safe Rust, `catch_unwind`, input limits, fuzzing (6.6) |
| Gatekeeper or antivirus blocks the binaries | Signing and notarization (section 9) |
| App store requirements for native code change (for example Android page size) | Mobile builds in CI; a test app built for both stores in phase 1 |
| Users on Intel Macs or other untargeted platforms can't import SVG files | Documented as a requirement; the importer shows a clear message. Adding a target is a CI change, not a design change |
| Contributors without Rust can't change the core | Prebuilt binaries in the package; Unity-side work needs no Rust |
| Different triangulation changes antialiasing slightly | Accept within the threshold; the visual tests decide |
| usvg API changes between versions | Pin versions; the ABI isolates C# from them |
| The C# bindings drift from the Rust ABI | Generated by csbindgen on every build; CI fails on a stale `NativeMethods.g.cs` |

## 15. Decisions and open questions

Decided:
- Targets: Windows x64, Linux x64, macOS arm64, iOS arm64, Android arm64 (section 3).
- Runtime import uses the native core on those targets; the legacy C# parser is removed (section 8).
- C# bindings are generated with csbindgen (6.3).

Open:
1. Should text conversion use only system fonts in the Editor, or also fonts in the project? At runtime, only project fonts are reliable (6.5).
2. Is a separate `svgimporter-cli` useful as a public tool, for example for CI pipelines that pre-check SVG files?
